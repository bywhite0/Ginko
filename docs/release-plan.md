# 版本迭代与发布方案

采用事件可靠性、记忆受众、任务生命周期与预算控制四项约束。版本范围与功能验收见 [路线图](roadmap.md)，
本文规定版本命名、候选验证、发布记录及升级回滚。

本方案按单维护者、单实例、专用测试会话逐步扩展设计。先做小范围受控部署，以验收结果决定发版，
不承诺固定交付日期。每周检查一次当前版本的阻塞项、验证记录和实际费用；
后续版本可以调整范围，但不得用版本号代替功能验收。

## 当前基线与发布范围

- 软件版本为 `0.1.0`，人格资源版本为 `1.0.0`，SQLite schema 为 `1`。
- `0.1.0` 表示当前代码版本，尚未正式发布。范围及剩余门槛见 [发布准备](releases/0.1.0.md)。
- 本版验证范围为离线基础能力、构建及独立环境安装，不包含真实平台、模型应答或人格表现。
- 已配置 GitHub Actions 的 Ubuntu / Windows 检查矩阵、产物清单、摘要、独立环境安装验证及产物留存。
  配置存在不代表远程检查已通过；结果以对应提交的 CI 记录为准。自动发版与升级回滚工具仍待接入。
- 默认交付源码包与 wheel，用于本地或受控部署。暂不增加容器、独立可执行文件和自动升级渠道。
  公开分发前须确认 [许可与来源](licensing.md) 中代码、人格及第三方组件的分发范围。

## 版本规则与候选阶段

Python 包版本采用 PEP 440：`0.2.0a1` → `0.2.0b1` → `0.2.0rc1` → `0.2.0`。
Git 标签对应 `v0.2.0a1`、`v0.2.0b1`、`v0.2.0rc1`、`v0.2.0`。

| 版本类型 | 使用条件 | 兼容要求 |
|---|---|---|
| `0.y.0` | 增加一项可独立验收的主要能力，如首个平台、记忆或图片输入 | 0.x 期间的破坏性变更也升次版本，并给出迁移和回滚边界 |
| `0.y.z` | 已有能力的修复、依赖或已支持端点的兼容修正 | 不改变已承诺的配置、数据和行为契约；人格与提示词行为变更仍须评审 |
| `aN` | 实现一个完整切片，用离线回放和故障注入证明机制 | 可调整接口；功能状态标为实验性 |
| `bN` | 在明确的测试账号、会话白名单和预算内验证真实调用 | 仅开放本轮范围，记录平台及模型组合 |
| `rcN` | 范围、配置、依赖与提示词冻结，验证安装、升级及运行表现 | 实质变更产生新候选并重验受影响门槛 |
| 无后缀版本 | 该版本的共同门槛和专属验收均通过 | 只承诺发布说明中列出的能力和经过验证的组合 |
| `1.0.0` 及以后 | 已公开的配置、存储迁移、事件与插件边界可以承担兼容承诺 | 破坏性变更升主版本；稳定版仍不表示支持任意平台或模型 |

一次版本推进顺序为：`0.1` 基础工程 → `0.2` 单平台文本 → `0.3` 最小记忆 →
`0.4` 第二平台文本 → `0.5` 图片输入 → `0.6` 自主活动 → `0.7` 工具与受控改进 → `1.0` 稳定运行。
在 `0.3` 深入记忆工程前，先完成第二平台的少量真实事件契约试验；完整接入到 `0.4` 验收。

软件、人格和数据库版本独立记录。人格及锚定规则只有维护者审核后才能更新 manifest 并生效；
普通聊天、记忆抽取和候选提示词无权修改。任务提示词先随代码提交定位，暂不另建版本服务。
依赖或模型服务端行为即使未改变代码，也应触发对应能力的复验。

## 每个版本都必须通过的门槛

从干净检出、锁定依赖的环境执行以下命令，Windows 与 Linux 的结果分别记录：

```powershell
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run pytest
uv run ginko smoke
uv build
uv run python scripts/verify_release.py
```

现有 CI 已配置这些命令。验包脚本检查 sdist、wheel 文件清单、版本及其与当前源码的一致性，
仅允许明确列出的代码、人格资源和工程文件。它在源码目录外的新虚拟环境中，安装锁定的生产依赖
与构建出的 wheel，执行 `ginko doctor`、`ginko smoke` 和 `ginko persona`，并检查实际导入位置。
依赖安装可能访问包索引，应用检查仍完全离线。

成功后 `dist/verification.json` 保存平台、时间、版本、Git 基线及工作区状态、产物成员、摘要和
安装检查结果；`dist/SHA256SUMS` 保存两个产物的摘要。失败时不保留旧的成功摘要供发布使用。
CI 按操作系统保存产物与报告；报告只证明该次检查，工作区构建不冒充正式签名提交的产物。
首次正式发布必须在最终提交上重新构建及执行验包，不能用源码目录下的测试代替。

跨版本保留以下行为回归，新增实现按实际风险补测试，不用重复断言实现细节充当覆盖：

- 重推事件不产生重复的已提交决策或出站意图；崩溃后计算可能重做，付费尝试仍逐次独立计费。
  角色、机器人账号、会话类型及线程的命名空间互不混淆。
- 入站已落库时重启能恢复；同一角色状态有序提交；过期 worker 无法提交。
  活动累计尝试次数和截止时间跨重启保留，等待期间接入仍能收包。
- 决策完成与出站意图同事务提交；确认发送不重复；回执丢失进入 `unknown`，不被自动重领。
- 费用按实际尝试预留；日/月额度耗尽后不发起新的付费请求；流式中断或用量缺失保留预留。
  原尝试结果未知时不盲目补发；只有既定错误分类允许再次调用时，才使用新尝试 ID 和新预留。
- 记忆检索先执行角色与受众过滤。私聊内容、画像和派生摘要均不得越过授权；撤回、更正、解绑及
  撤销共享必须影响后续访问。尚未接入记忆存储的版本只报告策略测试，不宣称完成检索隔离。
- 未通过结构和业务校验的模型输出不进入发送或记忆写入。人格、语言与关系称呼由固定探针加人工抽样检查。

从 `0.2.0rc1` 起，首次接入或改变平台、模型协议、持久状态行为的候选，默认在受控会话观察至少
连续 72 小时且完成 30 次正常定向文本往返，并进行一次受控停启及发送回执丢失演练。
样本不足则延长观察；接口或持久化相关变更后重新计时。纯文档变更无需真实模型调用。
这个门槛用于发现运行问题，不作为对话质量的统计保证。

故障场景优先用模拟端点和脱敏回放验证。真实验证使用既定预算与专用测试目标，不能为了凑样本越过硬额度。
首个模型至少人工评审 10 个固定人格、关系称呼与语言场景；后续候选沿用同一组基线，新增失败样例进入回归集。

发布阻塞项包括重复发送、记忆越权、无预算调用、状态或迁移损坏、人格未经审核生效以及已支持组合的
关键链路失败。未修复时停止该候选晋级。对话自然度等尚待改进的表现可以记录为已知限制，但必须能关闭实验能力。

## 平台与模型的支持记录

`0.2` 先验证一个 OneBot V11 协议端和一个模型端点、一种接口路线；第二平台在契约试验前从
Telegram / Discord 中选定一个。每增加一种组合，都单独填写验证记录，不能由相同 API 外形推导兼容。

| 记录项 | 必须明确的内容 |
|---|---|
| 平台 | 适配器与协议端版本、会话类型、稳定去重键、确认与补拉能力、回执和限流语义 |
| 模型 | 提供方、端点、模型标识及可获得的修订号、SDK 版本、接口路线、最近验证日期 |
| 输出 | JSON Schema 子集、根对象要求、结构及业务校验、拒绝、空响应与截断的处理 |
| 流与费用 | 结束状态、请求超时、用量缺失处理、价格表日期、最坏费用估算及每次重试计费 |
| 媒体 | 支持的真实格式、单图尺寸、图数、总字节数与费用上限；文本阶段明确标为未接入 |

吸收上游 Schema 兼容经验时，转换留在 provider 边界；仅对实测需要的限制做适配，转换后的请求也须测试。
完整 JSON 代码围栏如需支持，必须作为明确规则，在去除包裹后重新严格校验；不增加通用 JSON 修补链、
静默模型切换或无限重试。费用估算无法给出可靠上界时，该端点不进入受支持组合。

实际消息默认使用简洁自然的中文，专名与外语按上下文选择；语言规则不修改内部结构字段。
任何人格表达调整均经过维护者评审，不能借兼容性修复绕过人格变更要求。

## 发布操作与交付记录

以 `main` 集成可验证切片，用版本标签固定发布；只有已部署版本需要独立修复时才建立对应维护分支。
正式发布前确定托管目标和分发渠道；自动上传及包索引发布尚未接入。

1. 确认本版本范围、未完成项及迁移影响，更新 README、架构和路线图；候选说明写明实际验证边界。
2. 同步 `pyproject.toml`、`src/ginko/__init__.py` 与 `uv.lock` 中的项目版本。人格与 schema 只在各自变更时升级。
3. 在最终候选上完成共同门槛、版本专属验收和需要的运行观察，检查产物包含的资源。
4. 正式版本号产生新的签名发布提交后，重新执行共同检查、构建和安装包 smoke；核对除版本元数据外是否还有变动。
5. 维护者审核发布记录后，对通过验证的最终提交创建签名标签，保存该提交对应的构建产物及摘要。
   Git 签名操作在可访问签名密钥的 GPG 环境执行，不关闭签名规避问题。
6. 部署时先记录现有版本组合和数据备份，再按升级步骤停止、迁移、启动和验证；保留上一可用代码与产物。
   托管发布以后只上传已核对的产物，不从另一个未验证提交重新构建。
7. 已发布标签不移动，产物不覆盖；发布后发现缺陷使用新的补丁版本。正式运行的失败样例纳入下一次回归。

每份发布记录至少包括：

- 版本、最终提交 SHA、标签、构建时间、Python 与锁文件标识、产物 SHA-256。
- 已完成能力、实验能力、未验证能力、已知限制与实际启用的功能配置。
- 人格版本、提示词提交、配置格式版本、数据库 schema 及允许升级的来源版本。
- 平台/模型支持记录、检查命令结果、运行观察时段、故障演练与人工评审结果。
- 升级步骤、是否需要停机、回滚允许条件、数据恢复方式及负责审核的人。

这份记录可以直接放在发布说明中，不先增加一套发布管理服务。配置格式版本从真实配置接入时建立。
发布包与公开说明不包含凭据、真实聊天记录、私有记忆、数据库备份或未经授权的来源材料。
人格资源的分发范围与代码许可分别确认，见 [许可与来源](licensing.md)。

## 升级与回滚

`0.1.0` 仅能创建 schema 1 或打开同版本数据库，遇到其他版本会拒绝打开；它还没有迁移器。
第一次 schema 变化须同时交付版本检查、可验证的迁移步骤和备份恢复演练。
优先采用增加字段或表的兼容迁移；不能默认旧二进制支持新 schema，也不能靠降低 `user_version` 回退。

升级前停止接入和新的付费尝试，让在途工作在有界时间内收敛；保留未完成活动、未结算费用及投递状态。
关闭所有 SQLite 连接后复制完整数据库，或使用 SQLite 一致性备份接口；WAL 活跃时不能仅复制主文件。
在备份副本上验证迁移，并记录最后提交的事件、出站及预算状态，随后才升级运行库。

| 情况 | 处理方式 |
|---|---|
| 代码、提示词或人格表现退化，数据兼容 | 停止新增活动，切回已审核的上一组合，保留当前数据库与账本 |
| 新代码已写入旧代码不认识的 schema | 停止服务，选择已验证的数据迁移或前向修复；未经验证不降级运行 |
| 必须恢复较早备份 | 先核对备份之后的事件、已发送回执、未知投递、预算预留/支出，以及授权撤销和删除记录 |
| 无法完整核对恢复差异 | 保持付费调用和发送关闭，先恢复审计与核对能力，不能以清空账本或重排队解除阻塞 |

恢复不能把 `sent` 变成待发，不能自动重投 `unknown`，不能释放未知用量预留，也不能复活已经失效的活动。
恢复旧记忆快照还必须保留之后发生的撤权、删除与派生失效；代码回滚不等于把运行世界回到旧时间点。
`0.7` 的影子实验使用隔离业务数据库和配置，不能发送平台消息或写入生产记忆与人格文件；
实际费用仍经过统一预算入口累计，不能借隔离实验绕过总额度。

## 近期实施顺序

当前优先完成 `0.1.0` 的发布审核与最终提交验证，范围与剩余门槛见
[0.1.0 发布准备](releases/0.1.0.md)。维护者审核、最终签名提交和标签单独记录。
之后再推进 `0.2` 的配置与支持组合、单实例生命周期、预算约束的模型调用、文本决策与投递，
最后完成故障演练和受控试运行。本方案本身不提升软件版本或创建标签。
图片、主动社交和工具的接口仅在对应版本出现真实调用需求时实现。
